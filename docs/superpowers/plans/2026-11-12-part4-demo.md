# Part 4 — The Demo Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn Élégance into a self-cleaning showroom: a prospect taps **Essayer la démo** on `/admin` and uses the owner side with a shared demo account that sees masked phone numbers and can't enable notifications; the demo resets itself every night (and on demand by the product owner) to its original settings plus a fresh week of fake bookings — touching nothing outside the demo salon.

**Architecture:** A `demo` flag on `salons` and a `role` (`owner` | `demo`) on `private.staff`. A private `demo_settings` row per demo salon holds the public demo login and a snapshot of the salon's original catalogue/settings (a `provision_salon`-shaped payload captured at setup). Masking and restrictions are enforced in SQL by role (`admin_list_bookings`, `admin_update_booking`, push subscription), not just in the UI. `private.demo_reset(salon_id)` deletes the demo salon's bookings, prospect-added items and push subscriptions of demo accounts, re-applies the snapshot and generates fake bookings; `pg_cron` runs it nightly, and `admin_reset_demo()` lets an `owner` of the demo salon run it now. A small `pnpm setup-demo <salon-id>` script creates the demo account and snapshot.

**Tech Stack:** Supabase Postgres (migrations, pgTAP, `pg_cron`), React 18 + TS + React Query, Vitest, Node script with `tsx`.

**Spec:** `docs/superpowers/specs/2026-11-11-multi-salon-design.md` — section "Part 4 — The demo", and Parts 1–3 isolation rules. `CLAUDE.md` § Salons / Owner settings / Hosting.

## Global Constraints

- Branch `feat/part4-demo` from `main` (`0e28005`, Parts 1–3 merged and live). Never edit migrations up to `20261114100000_salon_branding.sql` (live).
- **Isolation (Parts 1–3):** every new table in `public`/`private` has `salon_id` NOT NULL FK + RLS; new functions callable by `anon`/`authenticated` get isolation tests in `10_isolation.test.sql` and a name in `11_guard.test.sql`; owner functions never take a salon id from the caller. Service-role-only functions are revoked from public/anon/authenticated. No blanket `revoke … on all functions in schema private`.
- **The reset touches only the demo salon's rows** (`salons.demo = true` checked inside the function) — an isolation test proves another salon's data is unchanged after a reset.
- **Spec decisions (product owner):** shared demo state is accepted; client phone numbers are **masked for the demo account** (`05•• •• •• 12`: keep the first 2 and last 2 digits, bullets `•` for the rest, grouped like the app's phone format); **"Réinitialiser la démo" only for the product owner's own staff account** (role `owner`) in the demo salon; prospects may still edit text; **the demo never notifies or messages anyone except the product owner** — the demo account cannot subscribe to push, and in the demo the WhatsApp "message to the client" opens WhatsApp to the **salon's** number (the product owner's), not the client's; **abuse limits stay on** (check them against a realistic pitch and report; don't silently disable).
- **Reset time:** ~03:00 Africa/Algiers = `0 2 * * *` UTC (Algiers is UTC+1 all year).
- **Fake bookings:** for each of the next 7 days that is open (`private.day_hours` returns a row), 3–5 bookings spread over active stylists inside opening hours, never overlapping per stylist, a mix of `confirmed` and `pending` and of `online`/`staff` sources (at least two `pending` in the week), names from a fixed list of plausible Algerian first names, phones `05xxxxxxxx` from a reserved fake range (`0550000000`–`0550000999`), prices/durations from the services. Deterministic per date (seeded by the date) so tests are stable.
- **Demo login** is public by design (the data is fake): it is returned only for a salon whose `demo` flag is true.
- Every UI string through `t()` (fr + ar); logical CSS; lucide-react only; phone layout at 360 px.
- Verify with `supabase db reset && supabase test db`, `supabase db lint --level warning --fail-on warning`, `pnpm test && npx tsc -b`.

## Review Focus

1. **The demo account edits a booking whose phone it only sees masked** (renames the client, moves the time) → saves without `invalid_phone` and without overwriting the real (fake) phone with the bullets. (Task 2.)
2. **A prospect adds a service/stylist, hides others, closes every day, deletes days off** → after a reset the salon is exactly back to its snapshot and the added items are gone; no booking references a deleted item. (Task 3.)
3. **The reset is called on a non-demo salon id** (by mistake, or a crafted call) → nothing changes and it raises `not_demo`. (Task 3.)
4. **The product owner's own account in the demo salon** → sees real phones, can subscribe to push, sees and can use "Réinitialiser la démo"; the demo account sees none of these. (Tasks 2, 4.)
5. **A prospect books online from the pitch phone 6 times in an hour** → document what the per-IP limit (5/hour) does and recommend; nothing silently disabled. (Task 6.)

**Interfaces:**

  - `private.staff.role text not null default 'owner' check (role in ('owner','demo'))` (existing rows → `owner`).
  - `private.demo_settings (salon_id text primary key references public.salons on delete cascade, login_email text not null, login_password text not null, snapshot jsonb not null, updated_at timestamptz not null default now())`, RLS on, no grants to anon/authenticated.

Re-running replaces login and snapshot.

### Task 3: Reset — nightly and on demand

**Files:** Create `supabase/migrations/20261115100100_demo_reset.sql`, `supabase/tests/database/17_demo_reset.test.sql`; modify `10_isolation.test.sql`, `11_guard.test.sql`

**Interfaces:**
- `private.demo_fake_bookings(p_salon_id text, p_from date, p_days integer) returns integer` — inserts fake bookings per the Global Constraints rules, returns how many.
- `private.demo_reset(p_salon_id text) returns void` — security definer; raises `not_demo` unless `salons.demo` is true for that id. In one transaction, for that salon only: delete its bookings; delete its `stylist_days_off`, `salon_closed_dates`; delete push subscriptions of its `demo`-role staff; delete services/stylists (and their links) whose ids are not in the snapshot; re-apply the snapshot through `public.provision_salon(snapshot || {"id": salon_id})` (it keeps every listed key); then `demo_fake_bookings(salon, today Algiers, 7)`.
- `private.demo_reset_all() returns void` — resets every salon with `demo = true`.
- `public.admin_reset_demo() returns void` — `not_authorized` unless the caller is staff with role `owner` of a salon whose `demo` is true; calls `demo_reset(my_salon())`. Granted to `authenticated`; registered in `11_guard`.
- `create extension if not exists pg_cron` and `cron.schedule('demo-nightly-reset', '0 2 * * *', 'select private.demo_reset_all()')` (idempotent: unschedule an existing job of that name first).
